# Calls (audio)

Audio calls go client to client. Video is not supported: it
would require a codec together with frame fragmentation and reassembly, for a
picture rate an I2P tunnel cannot sustain.

## Principle

No direct contact is attempted between peers, direct connections being harmful to
privacy. A call is negotiated through ordinary E2E messaging and the media is
carried over a
one-time hidden-network tunnel, so no server or facade ever sees call traffic.

## Transport

Media is carried over **I2P RAW datagrams** (UDP-like, low
overhead), one short-lived destination per call, torn down when the
call ends. RAW carries no per-packet source (so a frame stays small) and no
I2P-layer authentication - the call layer authenticates every datagram itself
(see Media encryption). Datagrams are the appropriate transport for realtime
media: a reliable stream would retransmit, and a late retransmitted frame is
useless.

An audio frame always fits in a single datagram, so nothing is ever fragmented.

### Tunnels

The media destination uses **minimal-length tunnels** (one hop each way, no
length variance) regardless of the tunnel profile the user picked for everything
else, the setting with the largest effect on latency and jitter for realtime media. This does not weaken identity anonymity: the media destination is
one-time and unlinked from the user's identity destination, so a short tunnel
there exposes nothing about who the user is. Variance is off so the path length
cannot change mid-call.

### Path probes

A media destination may measure the paths its datagrams take and send its audio
on the fastest. It sends a **probe**: a 9-byte RAW datagram to I2P port 7, byte 0
`1`, bytes 1-8 an id of its choosing, big-endian. An implementation **should**
answer a probe at once with an **echo**: the same 9 bytes with byte 0 `2`, to port
7 of the destination it sends this call's media to (a RAW datagram names no
sender), on the path that media takes. Media stays on port 0, so a probe never
reaches the decoder, and a side that does not answer only costs its peer the
choice of path.

### Encrypted LeaseSet (b33)

The call's media destination publishes an **encrypted LeaseSet2 (b33)**, like
every other Bazarish destination. An implementation must therefore be able to
send RAW datagrams to a blinded address: routers that address datagrams by
identity hash alone cannot carry this media, and how a given one is made to do it
is for that implementation to document. The destination is one-time and torn
down with the call, and its b33 routing address is shared only with the peer
inside the E2E-encrypted invite.

An I2P STREAM channel may be added later for in-call service messages; the media
itself stays on datagrams.

## Codecs

Audio: **Opus**, 48 kHz mono, 20 ms frames (the standard VoIP trade-off). Lost
frames are concealed by Opus; late or duplicate frames are dropped.


## Media encryption

The I2P tunnel encrypts the transport, but media is additionally protected
end-to-end, independent of the transport, with **AES-256-GCM** (a standard
primitive; no custom construction). The 32-byte key is generated by the caller
and carried in the call.invite, which is itself E2E-encrypted to the peer, so the
key never reaches any server. Each datagram is `nonce || AES-256-GCM(payload)`,
where the 12-byte nonce is `role(1) || track(1) || heard(1) || 0 || sequence(8, big-endian)`:

- **role** separates the two call directions: 1 for the caller, 2 for the callee.
- **track** is 0 for audio and leaves room for a second stream. The receiver reads
  it from the cleartext nonce to demultiplex; tampering with it fails the tag.
- **heard** is 1 once the sender has opened a datagram from its peer. A side plays
  nothing until it opens a datagram with `heard` set.
- **sequence** is monotonic per (role, track), so a (key, nonce) pair is never
  reused.

The audio payload is the Opus packet.

## Signaling message types

Call signaling is ordinary Layer-2 content (see `../Messages.md`): each signal is
a `content`-class delivery whose end-to-end payload carries the `call.*` type.
Server-side components see only opaque blobs of a generic message.

| Type | Direction | Payload |
|---|---|---|
| `call.invite` | caller -> callee | `callId`, `dest` (the caller's media b33 routing address), `key` (base64 per-call media key), `sentAt` |
| `call.ring` | callee -> caller | `callId`. Sent when a device of the callee presents the call. Until it arrives the caller only knows the invitation reached their server; from it, the caller's screen shows their device is ringing and the ringing tone starts |
| `call.accept` | callee -> caller | `callId`, `dest` (the callee's media b33 routing address) |
| `call.decline` | callee -> caller | `callId`, `reason` (`declined` / `busy` / `refused`). Honoured only while the caller is still calling: with several devices on one account, one of them answering and another refusing must not end the call that was answered |
| `call.end` | either | `callId` |
| `call.taken` | device -> the account's own devices | `callId`, `device`. Self-delivered (`DeviceSync.md`): every device of an account is shown the same invitation, and the one that answers or refuses stops the others. They drop the call without recording anything - the device that took it owns the outcome |

Adding or evolving a call signal is a client-only change.

Media is real-time and the rest of a client's traffic is not. How an
implementation keeps the two from competing - for threads, for a router's
workers, for anything else it shares - is an implementation matter and belongs in
its own documentation.

An invitation is answered within **60 seconds** of its `sentAt` (the field every
message carries) or not at all, and both sides count that window from the same
`sentAt`:

- The caller waits at most 60 seconds after it sent the `call.invite`, delivered
  or not, ringing or not, then ends the call with `call.end`.
- A callee **must** drop a `call.invite` that arrives 60 seconds or more after its
  `sentAt`, or that carries no `sentAt`. Such an invitation is not shown, not
  answered with any signal and not recorded: the mailbox holds what it is given
  until the device fetches it, so it can arrive long after the caller stopped
  waiting.
- An invitation that arrives in time rings only for what is left of the window.
  The window is counted from the earlier of `sentAt` and the arrival, so a callee
  whose clock runs behind the caller's never rings longer than 60 seconds.

Neither side requires a signal from the other in order to stop ringing.

The end of a call and its beginning are two mailbox items, and the mailbox does
not guarantee the order in which they are delivered. A callee that has seen
`call.end` or `call.decline` for a `callId` **must** ignore a `call.invite` for
that same call, whenever it arrives. Neither rule needs a new field: `callId`
and `sentAt` are already on the wire.

## Flow (I2P)

1. **Caller** builds a one-time RAW datagram destination, generates a per-call AES key, and sends a `call.invite` carrying its media b33
   and the key over the normal E2E delivery path.
2. **Callee** receives the invite (on sync), alerts the user, and answers the
   caller with `call.ring` so that the caller's state is known rather than
   inferred. On acceptance it builds its own RAW datagram destination, replies
   with `call.accept` carrying its media b33, and notifies its own other devices
   with `call.taken`.
3. Both sides now know each other's media destination and the shared key. Each
   captures the microphone, encodes Opus, AES-256-GCM-seals each datagram and
   sends it to the peer's b33; received datagrams are opened, decoded and played.
   Nothing is played until media has been observed in **both** directions: what
   arrives before that belongs to a path still being established, and playing it
   produces broken audio immediately before the call starts. A side with no audio
   to send - muted, or with no frame from the microphone - sends a datagram with
   an empty payload at least every 500 ms, and a side that has received nothing
   for 20 seconds ends the call.
4. Either side hangs up with `call.end`; the media engine and the one-time
   datagram destination are torn down.

Call media requires RAW datagrams addressed to a b33 destination. Any router that
carries both serves this protocol; how a client obtains one, and what it tests
that against, is for that client's implementation to document.

## Busy, refusal and loss

- **Busy.** A device already in a call answers a further `call.invite` at once
  with `call.decline`, reason `busy`, and does not ring; there is no call waiting.
  Two people who call each other at the same moment both receive `busy`.
- **Calls turned off.** Incoming calls are allowed by default. An account can
  turn them off entirely, and separately for one contact; an invitation that
  arrives while they are off is answered at once with `call.decline`, reason
  `refused`, and does not ring. The settings travel only to the account's own
  devices and are published nowhere; the refusal conveys nothing beyond
  unavailability at that moment.
- **Loss.** A receiver decodes each datagram as it arrives. A datagram whose
  sequence is not past the last one played is dropped, and a gap of up to five
  frames (100 ms) is filled by Opus loss concealment; there is no reordering and
  no adaptive jitter buffer.
