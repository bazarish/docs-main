# Calls (audio)

Status: audio calls implemented (client-to-client). Video is not supported: it
would require a codec together with frame fragmentation and reassembly, for a
picture rate an I2P tunnel cannot sustain.

## Principle

No direct contact is attempted between peers, direct connections being harmful to
privacy. A call is negotiated through ordinary E2E messaging and the media is
carried over a
one-time hidden-network tunnel, so no server or facade ever sees call traffic.

## Transport

Media rides **I2P RAW datagrams** (UDP-like, low
overhead) over the embedded i2pd router, one short-lived destination per call, torn down when the
call ends. RAW carries no per-packet source (so a frame stays small) and no
I2P-layer authentication - the call layer authenticates every datagram itself
(see Media encryption). Datagrams are the right fit for realtime media: a
reliable stream would retransmit, and a late retransmitted frame is useless.

An audio frame always fits in a single datagram, so nothing is ever fragmented.

### Tunnels

The media destination uses **minimal-length tunnels** (one hop each way, no
length variance) regardless of the tunnel profile the user picked for everything
else, the single biggest latency and jitter lever for realtime media. This does not weaken identity anonymity: the media destination is
one-time and unlinked from the user's identity destination, so a short tunnel
there exposes nothing about who the user is. Variance is off so the path length
cannot jump mid-call.

### Encrypted LeaseSet (b33)

The call's media destination publishes an **encrypted LeaseSet2 (b33)**, like
every other Bazarish destination. This requires routing RAW datagrams to blinded
(b33) addresses: stock i2pd routes datagrams only by identity hash, so the
datagram-to-b33 routing is a patch carried in the **embedded `libi2pd_bazarish`**
(in-process; no external router). Without it the media never arrives. The
destination is one-time and torn down with the call, and its b33 routing address
is shared only with the peer inside the E2E-encrypted invite.

An I2P STREAM channel may be added later for in-call service messages; the media
itself stays on datagrams.

## Codecs

Audio: **Opus**, 48 kHz mono, 20 ms frames (the standard VoIP trade-off). Lost
frames are concealed by Opus; late or duplicate frames are dropped.


## Media encryption

The I2P tunnel encrypts the transport, but media is additionally protected
end-to-end, independent of the transport, with **AES-256-GCM** (a standard
primitive; no custom construction). The 32-byte key is generated by the caller
and carried in the call.invite, which is itself E2E-encrypted to the peer, so the
key never reaches any server. Each datagram is `nonce || AES-256-GCM(payload)`,
where the 12-byte nonce is `role(1) || track(1) || 0 0 || sequence(8, big-endian)`:

- **role** separates the two call directions (caller / callee).
- **track** leaves room for a second stream alongside audio. The receiver reads
  it from the cleartext nonce to demultiplex; tampering with it fails the tag.
- **sequence** is monotonic per (role, track), so a (key, nonce) pair is never
  reused.

The audio payload is the Opus packet.

## Strict I2P requirement

A call is impossible without the embedded I2P router. Placing a call
(startAudioCall) or accepting one (acceptCall) brings the router up first and, if
I2P is unavailable, fails immediately with the typed, readable error
`I2P_UNAVAILABLE` - no call is placed and nothing half-starts.

## Signaling message types

Call signaling is ordinary Layer-2 content (see `../Messages.md`): each signal is
a `content`-class delivery whose end-to-end payload carries the `call.*` type.
Server-side components see only opaque blobs of a generic message.

| Type | Direction | Payload |
|---|---|---|
| `call.invite` | caller -> callee | `callId`, `media` (`audio`), `codec` (`opus`), `dest` (the caller's media b33 routing address), `key` (base64 per-call media key) |
| `call.ring` | callee -> caller | `callId`. Sent when a device of the callee presents the call. Until it arrives the caller only knows the invitation reached their server; from it, the caller's screen says their device is ringing and the ringing tone starts |
| `call.accept` | callee -> caller | `callId`, `media` (`audio`), `dest` (the callee's media b33 routing address) |
| `call.decline` | callee -> caller | `callId`, `reason` (`declined` / `busy` / `refused`). Honoured only while the caller is still calling: with several devices on one account, one of them answering and another refusing must not end the call that was answered |
| `call.end` | either | `callId` |
| `call.taken` | device -> the account's own devices | `callId`, `device`. Self-delivered (`DeviceSync.md`): every device of an account is shown the same invitation, and the one that answers or refuses stops the others. They drop the call without recording anything - the device that took it owns the outcome |

Adding or evolving a call signal is a client-only change.

A media destination is real-time and is treated as such below the protocol: an
implementation that pins destinations to worker threads **should** keep one for
media alone. In this one, the embedded router runs each destination on a
single-threaded lane, and a bulk transfer sharing that lane with a call is a call
that stutters while the file moves; the lane the media destination is put on
carries nothing else.

Both sides run their own ring timeout, so an unanswered call terminates without
user action. The caller's interval starts when the peer's device reported ringing,
or, if no such report arrived, when the invitation was delivered to the peer's
server; the callee's starts when the invitation arrived. Neither side requires a
signal from the other in order to stop ringing.

An invitation is only good while it would still be ringing. A signal carries the
`sentAt` every message carries, and a callee **must** ignore a `call.invite`
older than its ring timeout: the mailbox holds what it is given until the device
comes for it, so an invitation can arrive long after the caller stopped waiting,
and ringing for it then is ringing at nobody.

The end of a call and its beginning are two mailbox items, and the mailbox does
not promise the order they are handed over in. A callee that has seen
`call.end` or `call.decline` for a `callId` **must** ignore a `call.invite` for
that same call, whenever it turns up. Neither rule needs a new field: `callId`
and `sentAt` are already on the wire.

## Flow (I2P)

1. **Caller** builds a one-time RAW datagram destination on the embedded router
   (strict: I2P unavailable -> `I2P_UNAVAILABLE`), generates a per-call AES key, and
   sends a `call.invite` carrying its media b33 and the key over the normal E2E
   delivery path.
2. **Callee** receives the invite (on sync), alerts the user, and answers the
   caller with `call.ring` so that the caller's state is known rather than
   inferred. On acceptance it builds its own RAW datagram destination, replies
   with `call.accept` carrying its media b33, and notifies its own other devices
   with `call.taken`.
3. Both sides now know each other's media destination and the shared key. Each
   captures the microphone, encodes Opus, AES-256-GCM-seals each datagram and
   sends it to the peer's b33; received datagrams are opened, decoded and played.
   Nothing is played until media has been observed in **both** directions: what
   arrives before that belongs to a path still being established, and playing it
   produces broken audio immediately before the call starts. Muting keeps the
   capture loop running and transmits nothing.
4. Either side hangs up with `call.end`; the media engine and the one-time
   datagram destination are torn down.

## Implementation

- **common**: the embedded I2P RAW datagram endpoint (`bazarish::i2p::Endpoint`,
  embedded `libi2pd_bazarish`) and `aeadSeal`/`aeadOpen` (AES-256-GCM).
- **client lib**: `I2pCallTransport` (the per-call RAW datagram transport over the
  embedded endpoint); `AudioCodec` (Opus); `AudioIo` (device interfaces +
  synthetic backends for headless tests); `CallMedia` (the media engine: one
  capture thread and one receive thread); and the call signaling + state machine
  on `Session` (`startAudioCall` / `acceptCall` / `declineCall` / `endCall` /
  `setCallMuted` / `currentCall`).
- **CLI**: `bazarish-client call <account> <peer> [seconds]` and
  `call-answer` (drive the signaling loop; with the synthetic backends they give
  a headless end-to-end media path for integration testing).
- **GUI**: `CallScreen.qml` (peer, state, mute / end controls) plus the Qt
  Multimedia audio backends `QAudioSource` / `QAudioSink`.

Live-validated: I2P RAW datagrams round-trip over real I2P between two
destinations (b32 and b33). The audio codec round trip, the
AES-256-GCM seal/open (including tamper/wrong-key rejection), and the full
audio pipeline over an
in-memory loopback are covered by unit tests.

Call media requires RAW datagrams addressed to a b33 destination. Any router that
carries both serves this protocol; how a client obtains one is its own business.

## Open / not done

- **Jitter buffer** - playback is in-order with bounded packet-loss concealment;
  a deeper adaptive jitter buffer is a refinement.
- **Glare / busy** - a second incoming call while busy is auto-declined with
  `reason: busy`; richer call-waiting is future work.
- **Calls turned off** - an account may refuse incoming calls entirely (a privacy
  setting, on by default). An invitation is then answered at once with
  `reason: refused`, so the caller learns it instead of ringing into nothing. The
  caller's call control is unchanged: the setting may be re-enabled at any time and
  is not published. The refusal is the only signal, and it conveys nothing beyond
  unavailability at that moment.
