# Contact Admission: One-Time Delivery Tokens

Status: design draft (decided direction).

## Problem

A server stores incoming content only if the sender is an approved contact of the recipient. A naive contact list (recipient's approved UIDs on the server) is a readable social graph - unacceptable, since collectable metadata is a critical bug. The server must be able to *enforce* contact admission without being able to *read* the relationship.

## Scheme

A **delivery token** is a 256-bit random value generated by the recipient's client and handed to a contact over the E2E channel. Tokens are strictly single-use.

- The recipient's client registers `SHA-256(token)` values with its own server (mixed batches across all contacts, never grouped per contact).
- A sender attaches one unused token to each message, inside the sealed envelope (see `api/Federation.md`) - readable by the recipient's server only.
- The recipient's server hashes the presented token, looks it up in the mailbox's registered set, and **consumes it atomically with storing the message**. No match - delivery rejected.
- No signatures involved; plain hashing only (standard primitives).

What this yields:

- **No social graph at rest.** The server holds a flat set of opaque hashes per mailbox; nothing maps a hash to a contact.
- **Unlinkability.** Tokens are random and single-use; the server cannot link two messages to the same contact.
- **Replay protection.** A consumed token cannot be presented again, so token-gated messages cannot be replayed. Tokenless contact requests (which have no token to spend) are covered instead by the server's retained **seen-messageId set**: every admitted `messageId` is remembered independently of the stored blob's lifecycle, so an already-delivered envelope cannot be re-admitted even after it has been fetched, acked and swept from the mailbox (see `api/Federation.md`).
- **Targeted revocation still works.** The *issuing client* keeps the private bookkeeping of which tokens went to which contact. Revoking a contact = asking the server to delete that contact's unused hashes. The server learns only "these hashes died together" at the moment of revocation.

## Token lifecycle

1. **Issuance** - recipient's client generates a batch (default size TBD, e.g. 50-100) per contact, delivers it inside an E2E message, registers the hashes with its server (`POST /v1/messaging/tokens`, see `api/ClientApi.md`). Registration must precede or accompany delivery of the batch to the contact.
2. **Consumption** - exactly one token per accepted message. Processing order on the recipient's server: messageId dedup first (a retried message must succeed idempotently *without* consuming a second token - checked against both the pending blob and the retained seen-messageId set), then token lookup, then size/quota checks; the token is consumed only if the message is actually stored, and the `messageId` is recorded in the seen set on a successful store.
3. **Refill** - fully E2E, invisible to servers: when a sender's stash for a peer drops below a threshold, its client signals this in the E2E payload **and embeds one fresh token of its own** (`refillToken`, prepaying the reply); the peer's client auto-issues a fresh batch and delivers it as a `token-refill` message **spending exactly that prepaid token**. So the refill reply always lands - even when the peer currently holds none of the sender's tokens - and it never consumes the peer's own stash: the refill round-trip funds itself. Each direction has its own independent stash.
4. **Revocation** - `DELETE /v1/messaging/tokens` with the unused hashes issued to the revoked contact. Epoch reset (drop *all* hashes, re-issue to remaining contacts over E2E) remains the nuclear option, e.g. after client-state compromise.

Token bookkeeping (issuance records, registrations, spends) is private client state synchronized across the user's devices via the sync journal (`DeviceSync.md`). Two devices may race to spend the same outgoing token; the loser gets `DELIVERY_REJECTED` and retries with another token - messageId dedup prevents duplicates.

## Contact request bootstrap

A is not B's contact and B is not A's - the first exchange must bootstrap both directions:

1. A's client generates an initial token batch *for B*, registers its hashes on A's own server.
2. A sends a **contact request** to B: a tokenless delivery, flagged as a request, payload capped (default 8 KB, server-configurable via `--contact-request-limit`). The cap is on the delivered, CMS-sealed bytes and must comfortably exceed a real contact request: the E2E payload carries A's identity, the introduction message, A's self-chosen **display name** (`dn`, so B can seed a named friend - see "Display names" below), **a full reply-token batch for B** (`kTokenBatchSize`, 64 tokens), plus A's routing **bootstrap** - `{ sealing prekey, dest, servingKey }` (see `../Identity.md`) - without which B would not know where to send the acceptance, so a sealed request is roughly 4 KB. (A cap below that silently rejects every contact request with `CONTACT_REQUEST_TOO_LARGE`. No server fingerprint or server card: routing is by destination.)
3. B's user accepts -> B's client sends a **`contact.accept`** (`Messages.md`) *using one of A's tokens*; as B's first reply it carries B's batch and the same routing bootstrap in the E2E payload. A's client applies that bootstrap automatically (no user step) and surfaces a "accepted your request" note. Both directions are now live. The acceptance is a single button - **Agree**; there is no explicit decline.
4. B declines -> silent drop, nothing is sent (ignoring the request is the decline). A's client revokes the pre-registered hashes after a timeout.

Contact requests are the only tokenless path into a mailbox; they get a separate small quota and per-origin-server rate limiting.

## Display names and avatars

A contact's **display name** is a local label, captured once at add time - from the invite descriptor's optional `name` or from the alias used - and never refreshed from the peer afterwards. A later rename is local, mirrored only to the user's own devices (`DeviceSync.md`).

The label is symmetric across the first exchange. The requester A names B from the descriptor/alias it added by. So B is not left with a bare fingerprint, A's **contact request carries A's own display name** (`dn`); B adopts it as the initial local label for A, exactly once, **only when B holds no name yet** (it never overwrites a name B already set). This is a one-time seed, not a live name channel: a later rename on either side is never pushed to the other.

A user's **avatar** (square, compressed client-side to <= 500 KB) is exchanged only **after the dialog is mutually established**: the accepting reply carries the accepter's avatar, and the requester sends theirs on receiving that acceptance. A bare contact request neither carries an avatar nor triggers an automatic avatar reply, so nothing of a user's picture leaks to a party who has not yet been accepted. Both ride the silent `avatar` (and self-channel `device.*`) content types in `Messages.md`.

## First-contact discovery and co-location

Before A can send the contact request above it must learn B's routing (`{ sealing prekey, dest, servingKey }`). Two discovery paths exist:

- **Invite / alias** - A holds a self-verifying descriptor (fingerprint + serving destination + serving key) and fetches B's user-signed card **over I2P federation**, dialing B's serving destination directly. The card is verified against the fingerprint, so no server is trusted (see `api/FederatedResolve.md`).
- **By fingerprint** - A asks **its own server's facade** for B's routing (`GET /v1/account/contact`). This only works for a peer already known to be on A's own server and trusts that server for the routing. (CLI-only; not exposed in the GUI.)

**Co-location rule (mandatory).** Two clients of the same server always have *different* I2P destinations - every account owns one - so first-contact discovery **MUST** go over I2P (the invite/alias card fetch), **never** the facade contact lookup. A facade lookup tells the shared server "client A is asking for client B"; combined with both resolving to that server, it discloses that A and B are **co-located on it**. Routing discovery through I2P makes A's lookup of B indistinguishable from any other federation fetch, so the server cannot infer co-location. The facade by-fingerprint path is therefore only for cases where same-server membership is already not secret.

For the same reason the contact request **delivery** is routed by destination over federation (I2P), with a local store short-circuit **only** when the recipient's destination is identical to the sender's own - never inferred from the server knowing it happens to operate both distinct destinations. See `api/Federation.md`.

## What the server still learns (honest accounting)

- **Set size** ~= contacts x stash size - a degree estimate. Mitigation: clients may pad with dummy hashes.
- **Registration timing** - a batch registered right after an outgoing contact request hints that the batch belongs to that pending contact. Mitigation: random delays, pre-registration padding. Noted for the threat model; not a v1 blocker.
- **Traffic volume per mailbox** - unavoidable for any store-and-forward server.

## Anti-enumeration

A destination belongs to one user, and only their mail is stored in it. A
tokenless contact request naming any other mailbox is answered exactly like a
delivered one and dropped - refusing it would answer "whose destination is
this?" - and it never touches the seen-cache, so it cannot be used to censor the
real delivery of the same id. A token-bearing delivery for another mailbox is
refused like any other bad admission.

Invalid token, unknown mailbox, and a recipient not served here must be externally indistinguishable (single `DELIVERY_REJECTED` error). Detailed typed errors (e.g. `QUOTA_EXCEEDED`, which the sender must see explicitly) are returned only after a valid token has been presented - so only actual contacts can learn mailbox state.

## Open questions

- **Defaults** - batch size, low-stash threshold, per-mailbox hash cap (server config), contact-request quota.
