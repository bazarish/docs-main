# Contact Admission: One-Time Delivery Tokens

Status: design draft (decided direction).

## Problem

A server stores incoming content only if the sender is an approved contact of the recipient. Holding that approval as a list of identities on the server would constitute a readable social graph, which the threat model does not permit. The server must therefore be able to *enforce* contact admission without being able to *read* the relationship.

## Scheme

A **delivery token** is a 256-bit random value generated by the recipient's client and handed to a contact over the E2E channel. Tokens are strictly single-use.

- The recipient's client registers `SHA-256(token)` values with its own server (mixed batches across all contacts, never grouped per contact).
- A sender attaches one unused token to each message, inside the sealed envelope (see `api/Federation.md`) - readable by the recipient's server only.
- The recipient's server hashes the presented token, looks it up in the mailbox's registered set, and **consumes it atomically with storing the message**. Absence of a match is a rejected delivery.
- No signatures involved; plain hashing only (standard primitives).

Properties:

- **No social graph at rest.** The server holds a flat set of opaque hashes per mailbox; nothing maps a hash to a contact.
- **Unlinkability.** Tokens are random and single-use; the server cannot link two messages to the same contact.
- **Replay protection.** A consumed token cannot be presented again, so token-gated messages cannot be replayed. Tokenless contact requests (which have no token to spend) are covered instead by the server's retained **seen-deliveryId set**: every admitted `deliveryId` is remembered independently of the stored blob's lifecycle, so an already-delivered envelope cannot be re-admitted even after it has been fetched, acked and swept from the mailbox (see `api/Federation.md`).
- **Bookkeeping stays with the issuer.** The issuing client records privately which tokens were given to which contact; the server holds no such association. Unwanted correspondents are handled at the client (see *Token lifecycle*, item 4), so no revocation request is made to the server and no set of hashes is ever seen to be discarded together.

## Token lifecycle

1. **Issuance** - recipient's client generates a batch (**256 tokens**) per contact, delivers it inside an E2E message, registers the tokens with its server (`POST /v1/messaging/tokens`, see `api/ClientApi.md`). Registration must precede or accompany delivery of the batch to the contact.

   A token is not a random value alone. It is minted under a **mask** that belongs to one correspondent - `sha256(the account's static delivery secret || that correspondent's fingerprint)` - as `mask XOR (random || mark)`, where the mark is a fixed four-byte tail. The secret is drawn once with the account, travels with its backup, and never leaves it; the mask leaves only as a revocation request to the account's own server. To anyone else a token is 32 bytes indistinguishable from noise, and the shape is what makes point 4 possible.
2. **Consumption** - a message is admitted by **as many tokens as it weighs**: one per 30 KiB of sealed payload (`kBytesPerDeliveryToken`), never fewer than one, so a line of text costs one and the largest payload the protocol allows costs eighteen. The sender counts them out and puts them all in the envelope (`tokens`); the recipient's server computes the same number from the payload it is holding and refuses any envelope that does not carry exactly that many - what the sender claims to be paying is a claim, and the side that stores the bytes decides the price. Either all of them are consumed or none is: a delivery that fails partway puts back what it took. This is what makes a conversation cost what it always did while filling a mailbox costs the sender their stash. Processing order on the recipient's server: deliveryId dedup first (a retried message must succeed idempotently *without* consuming a second token - checked against both the pending blob and the retained seen-deliveryId set), then the count and the tokens themselves, then size/quota checks; the tokens are consumed only if the message is actually stored, and the `deliveryId` is recorded in the seen set on a successful store.
3. **Refill** - fully E2E, invisible to servers: when a sender's stash for a peer drops to the refill threshold (**128**, half a batch), its client signals this in the E2E payload **and embeds one fresh token of its own** (`refillToken`, prepaying the reply); the peer's client auto-issues a fresh batch and delivers it as a `token-refill` message **spending exactly that prepaid token**. So the refill reply always lands - even when the peer currently holds none of the sender's tokens - and it never consumes the peer's own stash: the refill round-trip funds itself. Each direction has its own independent stash.

   The threshold is half a batch because the ask can only ride on something the user is sending, and the answer waits on a correspondent who may be away for days: the headroom is what stops a long conversation, or a peer who is simply offline, from running the sender dry before anybody can answer. A stash that runs out anyway is **not** refilled over the tokenless path - a contact request is the only tokenless door into a mailbox, and a top-up over it would turn one narrow door into a channel anybody may knock on. What is left is a token from another device of the same account (`DeviceSync.md`), and a flood is ended by removing the contact, which revokes every token it holds.
4. **Reissue** - revoking a correspondent's tokens leaves them unable to answer, so an account that lifts a block hands out a fresh batch on the first message it writes to them, in the same `bootstrap` block a first reply uses. An unaddressed batch is added to what the receiving device already holds, never in place of it: at a first bootstrap there is nothing to replace, and later there is.
5. **Revocation** - per correspondent, and asked for by the account that issued the tokens. Its client sends that correspondent's mask (`POST /v1/messaging/tokens/revoke`); the server walks the tokens it holds for that user, keeps the ones whose XOR with the mask does not end in the mark, and drops the rest. It answers before the walk, which runs on a single thread shared by every user of the node: a user with a great many tokens costs a slow sweep, never a busy node. A token minted for another correspondent matches by accident with probability 2^-32, and its holder loses one delivery. Removing or blocking a contact revokes what they hold; an unspent token that is never revoked remains until it is spent or expires (`kTokenRetentionDays`), and deleting the account discards all of them.

   The cost of the shape is stated plainly: the server holds the tokens themselves rather than their hashes, so whoever can read a node's disk can spend what is on it; and two tokens minted for the same correspondent XOR to a value ending in four zero bytes, so a node can group a user's tokens by correspondent without being asked to revoke anything. Both are accepted in this protocol, where the node is trusted and the network is the threat.

Token bookkeeping (issuance records, registrations, expenditures) is private client state, synchronised across the user's devices through the sync journal (`DeviceSync.md`). Two devices may attempt to spend the same outgoing token; the second receives `DELIVERY_REJECTED` and repeats with another token, and deduplication by delivery id prevents a duplicate delivery.

## Contact request bootstrap

A is not B's contact and B is not A's - the first exchange must bootstrap both directions:

1. A's client generates an initial token batch *for B*, registers its hashes on A's own server.
2. A sends a **contact request** to B: a tokenless delivery, flagged as a request, payload capped (11700 bytes, the measured worst case; server-configurable via `--contact-request-limit`). The cap is on the delivered, CMS-sealed bytes and must comfortably exceed a real contact request: the E2E payload carries A's identity, the introduction message, A's self-chosen **display name** (`dn`, so B can seed a named friend - see "Display names" below), **a small reply-token batch for B** (`kRequestTokenBatchSize`, 16 tokens - the full 256 arrive with B's first reply, which is paid for; this one rides the tokenless path, so what it weighs is what a flood of requests costs B), plus A's routing **bootstrap** - `{ sealing prekey, dest, servingKey }` (see `../Identity.md`) - without which B would not know where to send the acceptance, so a sealed request weighs 11668 bytes at its worst, the authorship block that
introduces the sender's keys (`Messages.md`) being 5471 of them. The cap is that
number plus what the variable-length parts can add, and no more: room above the
worst case is room for a stranger to fill a mailbox with. (A cap below that silently rejects every contact request with `CONTACT_REQUEST_TOO_LARGE`. No server fingerprint or server card: routing is by destination.)
3. B accepts, and B's client sends a **`contact.accept`** (`Messages.md`) *spending one of A's tokens*. As B's first reply it carries B's batch and the same routing bootstrap in the E2E payload. A's client applies that bootstrap without user action and reports the acceptance. Both directions are then established. Acceptance is an explicit action; declining is not signalled.
4. B declines by taking no action: nothing is transmitted. The hashes A pre-registered expire under the retention policy.

Contact requests are the only tokenless path into a mailbox; they get a separate small quota and per-origin-server rate limiting. Two bounds, not one: **3 per minute** per serving destination (`kContactRequestsPerMinute`) says how fast they may arrive, and **30 waiting at once** (`kMaxPendingContactRequests`, counted over what the mailbox is still holding) says how many may pile up. Past either, the answer is the same transient refusal a rate-limited sender gets - come back later - which says nothing about who is served at that destination.

## Display names and avatars

A contact's **display name** is a local label, captured once at add time - from the invite descriptor's optional `name` or from the alias used - and never refreshed from the peer afterwards. A later rename is local, mirrored only to the user's own devices (`DeviceSync.md`).

The label is symmetric across the first exchange. The requester A names B from the descriptor/alias it added by. So B is not left with a bare fingerprint, A's **contact request carries A's own display name** (`dn`); B adopts it as the initial local label for A, exactly once, **only when B holds no name yet** (it never overwrites a name B already set). This is a one-time seed, not a live name channel: a later rename on either side is never pushed to the other.

A user's **avatar** (square, compressed client-side to <= 500 KB) is exchanged only **after the dialog is mutually established**: the accepting reply carries the accepter's avatar, and the requester sends theirs on receiving that acceptance. A bare contact request neither carries an avatar nor triggers an automatic avatar reply, so nothing of a user's picture leaks to a party who has not yet been accepted. Both ride the silent `avatar` (and self-channel `device.*`) content types in `Messages.md`.

## First-contact discovery and co-location

Before A can send the contact request above it must learn B's routing (`{ sealing prekey, dest, servingKey }`). Two discovery paths exist:

- **Invite / alias** - A holds a self-verifying descriptor (fingerprint + serving destination + serving key) and fetches B's user-signed card **over I2P federation**, dialing B's serving destination directly. The card is verified against the fingerprint, so no server is trusted (see `api/FederatedResolve.md`).
- **By fingerprint** - A asks **its own server's facade** for B's routing (`GET /v1/account/contact`). This only works for a peer already known to be on A's own server and trusts that server for the routing. (CLI-only; not exposed in the GUI.)

**Co-location rule (mandatory).** Two clients of the same server always have *different* I2P destinations - every account owns one - so first-contact discovery **MUST** go over I2P (the invite/alias card fetch), **never** the facade contact lookup. A facade lookup tells the shared server "client A is asking for client B"; combined with both resolving to that server, it discloses that A and B are **co-located on it**. Routing discovery through I2P makes A's lookup of B indistinguishable from any other federation fetch, so the server cannot infer co-location. The facade by-fingerprint path is therefore only for cases where same-server membership is already not secret.

For the same reason the contact request **delivery** is routed by destination over federation (I2P) in every case, including one in which the same server operates both destinations. No local short-circuit exists; the sending client performs the delivery, so no server is in a position to take one. See `api/Federation.md`.

## Residual disclosure to the server

- **Set size** is approximately the number of contacts multiplied by the stash size, which estimates the degree of the contact graph. Mitigation: clients may pad the set with unused hashes.
- **Registration timing**: a batch registered immediately after an outgoing contact request indicates that the batch belongs to that pending contact. Mitigation: randomised delay and pre-registration padding. Recorded in the threat model; not a release blocker.
- **Traffic volume per mailbox** is inherent to any store-and-forward server.

## Anti-enumeration

A destination belongs to one user, and only that user's mail is stored in it. A
tokenless contact request naming any other mailbox receives the same response as a
delivered one and is discarded; refusing it would disclose which user the
destination serves. Such a request does not enter the seen-set, so it cannot be
used to suppress the genuine delivery of the same id. A token-bearing delivery for another mailbox is
refused like any other bad admission.

Invalid token, unknown mailbox, and a recipient not served here must be externally indistinguishable (single `DELIVERY_REJECTED` error). Detailed typed errors (e.g. `QUOTA_EXCEEDED`, which the sender must see explicitly) are returned only after a valid token has been presented - so only actual contacts can learn mailbox state.
